What is a GPU?

The usual answer is “a chip with thousands of cores, so it’s faster.” That is true only for one shape of work, and even then the cores usually aren’t the limit. This page shows both halves of that sentence.

Two machines appear throughout. The CPU is an AMD EPYC 9654, a top-end server processor with 96 cores. The GPU is an NVIDIA H100 SXM, the chip most AI is trained on, with 16,896 lanes. A core is a worker that can follow its own list of instructions. A lane is a slot that does one arithmetic step at a time; on a GPU, lanes don’t get to choose their own instructions.

1 The shape of the work

A GPU’s lanes move in lockstep: on every tick of its clock they all carry out the same instruction (one step, like “multiply these two numbers”), each on its own piece of data. A CPU core can do whatever it likes.

Below, both machines get the same 16,896 pieces of work. The slider sets how many different kinds of work those pieces are split into. The GPU can only run one kind per tick, so every lane without that kind of work sits idle. The CPU’s 96 cores each run their own task and stay busy no matter what.

Thousands of lanes help only when thousands of pieces of work want the same instruction at the same moment. When each step needs the previous step’s answer, there is only ever one piece of work ready, and extra lanes don’t help at all.

The model: one piece of work per lane per tick. A CPU core does 2 per tick because it runs at roughly twice the clock speed. A real GPU is less rigid than this: its lanes come in groups of 32, and different groups can follow different instructions. Lanes within a group still have to march together, and that is the effect shown here.

2 Why AI is shaped like that

Almost all the arithmetic in an AI model is matrix multiplication: the same multiply-and-add, repeated an enormous number of times, with no piece waiting on any other.

To multiply two 8×8 grids of numbers, each of the 64 cells of the answer takes one row of the first grid and one column of the second, multiplies them pair by pair, and adds up the 8 products. That is 512 multiply-adds in total. No cell needs another cell’s answer, so they can be done in any order, or all at the same time.

AI is a near-perfect fit for section 1: one instruction, billions of independent pieces. That is why GPUs, built for drawing millions of pixels the same way, ended up running it.

3 The real ceiling is memory

Lanes can only work on numbers that have already arrived from memory. For most real work, the chip spends more time waiting for data than doing arithmetic.

Two numbers describe any chip. Peak compute is how many arithmetic operations it can do per second, counted in FLOP/s (floating-point operations, meaning arithmetic on decimal numbers). Memory bandwidth is how many bytes per second memory can deliver to it. The H100 does 989.4 TFLOP/s in bf16 (a compact 2-byte number format used in AI), dense, on its tensor cores (units built only for matrix multiplies). It reads memory at 3.35 TB/s. NVIDIA’s spec sheet also lists 1,979 TFLOP/s, but that figure assumes sparsity (half the numbers are zero and skipped); this page uses the dense figure throughout. The EPYC does 10.9 TFLOP/s in FP32 (4-byte numbers) and reads memory at 460.8 GB/s.

What matters is arithmetic intensity: how many operations your work does for each byte it fetches. Below a certain intensity, the chip runs out of data before it runs out of arithmetic. That crossover, the ridge point, is peak compute divided by bandwidth. For the H100 it is 295 operations per byte. For the EPYC it is 23.7.

The H100’s ridge sits 12.5× further right than the EPYC’s. Its arithmetic grew far faster than its memory, so work that keeps a CPU fully busy leaves a GPU waiting. A matrix multiply at around 100 operations per byte runs the EPYC at its full peak but holds the H100 to 33.9% of its peak.

4 Why the money goes where it goes

Memory is the expensive part. The H100 uses HBM (high-bandwidth memory): memory chips stacked on top of each other and placed right next to the processor, wired with thousands of connections. It delivers 3.35 TB/s, 7.3× what the EPYC gets from ordinary server memory, and it is one of the scarcest, most expensive parts of an AI chip. Every extra byte per second moves the ridge left and lets more real work reach peak speed.

A chatbot answering one person barely uses the arithmetic. To produce each word (a token), a language model reads every one of its weights (the learned numbers that make up the model) once, and does 2 operations with each: a multiply and an add. In bf16 each weight is 2 bytes, so that is an intensity of 1 operation per byte. That is the first preset in the chart above. At that intensity the H100 reaches 3.35 TFLOP/s of bf16 arithmetic: 0.34% of its 989.4 TFLOP/s peak. For a 70 billion-weight model, that means reading 140 GB per token, about 24 tokens per second, set entirely by memory. This is why providers batch many users together: each weight fetched serves every request in the batch, and it takes a batch of about 295 to reach the ridge.

Shrinking the numbers makes it faster without adding arithmetic. Quantizing (storing each weight in 8 bits instead of 16) halves the bytes to read, 70 GB instead of 140, while the operations stay the same. Intensity doubles, the chip reaches 6.7 TFLOP/s (still bf16 arithmetic; only the storage shrank), and the model produces about 48 tokens per second instead of 24. No extra compute was added, because compute was never the limit.

Assumptions: one user (batch of 1), weight reads dominate memory traffic, and the H100 runs at full bandwidth. The 70 billion-weight model is an example size. Every other number is computed from the two spec sheets above.
